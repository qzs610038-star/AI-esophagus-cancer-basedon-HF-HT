## 一、SSH 连接：一条命令背后的七层魔法

当你敲下 `ssh user@server` 时，发生了什么？

```
你的终端                         网络                         服务器
┌──────────┐                 ┌──────────┐                 ┌──────────┐
│ $ ssh    │ ──────────────→ │          │ ──────────────→ │ sshd     │
│ user@ip  │  Layer 1-4      │ 互联网    │  Layer 1-4      │ 监听:22  │
│          │  网络栈建立连接   │          │  网络栈接收       │          │
│          │                 │          │                 │          │
│          │ ─── Layer 5-6 ──│          │── Layer 5-6 ────│          │
│          │  SSH 协议握手    │          │  SSH 协议握手    │          │
│          │                 │          │                 │          │
│          │ ─── Layer 7 ────│          │── Layer 7 ──────│          │
│          │  密钥认证        │          │  密钥认证        │          │
└──────────┘                 └──────────┘                 └──────────┘
```

### 七层排查法（自底向上）

排障时永远从底层往上层查——底层不通，上层不可能通：

| 层 | 检查项 | 工具 | 本案例结果 |
|:---:|--------|------|:---:|
| **1-2** | 网线/网卡 | ping | ✅ RDP 通，跳过 |
| **3** | IP 路由 | tracert | ✅ 到达 117.71.0.118 |
| **4** | TCP 端口 | Test-NetConnection | ✅ 22 端口可达 |
| **5-6** | SSH 握手 | `ssh -vvv` | ✅ 版本协商通过 |
| **7** | 密钥认证 | authorized_keys 审计 | 🔴 Host Key 不匹配 |

## 二、SSH 的核心概念（排障必备）

### 2.1 公钥认证的完整流程

```
┌─ 你的电脑 ─┐                              ┌─ 服务器 ─┐
│             │                              │          │
│  🔑 私钥    │                              │  🔓 公钥  │
│  (绝密)     │                              │  (公开)   │
│             │                              │          │
│  ① 发送公钥 ──────────────────────────────→│  ② 查找匹配的公钥
│             │                              │     (在 authorized_keys 中)
│             │                              │     ↓ 找到！
│             │←── ③ 发送加密的随机挑战 ──────│  ③ 用公钥加密随机数
│             │                              │
│  ④ 用私钥解密│                              │
│    返回结果  │──────────────────────────────→│  ⑤ 比对结果
│             │                              │     匹配 → 登录 ✅
│             │                              │     不匹配 → 拒绝 ❌
└─────────────┘                              └──────────┘
```

### 2.2 认证涉及的文件

| 文件 | 位置 | 内容 | 谁持有 |
|------|------|------|:---:|
| 私钥 | `~/.ssh/id_ed25519` | 解密用的秘密钥匙 | 🔒 只有你 |
| 公钥 | `~/.ssh/id_ed25519.pub` | 加密用的公开钥匙 | 📤 发给服务器 |
| authorized_keys | 服务器 `~/.ssh/authorized_keys` | 允许登录的公钥列表 | 🖥️ 服务器 |
| sshd_config | 服务器 `C:\ProgramData\ssh\sshd_config` | SSH 服务配置 | 🖥️ 服务器 |
| known_hosts | `~/.ssh/known_hosts` | 信任的服务器指纹列表 | 📋 你自己 |

### 2.3 Host Key vs User Key（容易混淆）

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  Host Key（服务器身份证明）              User Key（你的身份证明）         │
│  ┌─────────────────────────┐           ┌──────────────────────┐      │
│  │ 服务器证明"我是我自己"     │           │ 你证明"我是合法用户"    │      │
│  │ 位置：/etc/ssh/ssh_host* │           │ 位置：~/.ssh/id_*     │      │
│  │ 验证者：你的 SSH 客户端   │           │ 验证者：服务器的 sshd   │      │
│  │ 记录在：known_hosts      │           │ 记录在：authorized_keys│      │
│  └─────────────────────────┘           └──────────────────────┘      │
│                                                                      │
│  🔑 本案例的突破点：比对了两台机器的 Host Key，发现完全不同              │
│     → 证明 117.68.10.96:22 不是我们要连的机器                          │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

## 三、实战案例：PFMval 服务器 SSH 排障全记录

### 3.1 初始症状

```
$ ssh AIPatho1@117.68.10.96
AIPatho1@117.68.10.96: Permission denied (publickey,gssapi-keyex,gssapi-with-mic).
```

**表面现象**：权限被拒，服务器不接受我的密钥。

**错误的第一反应**（6 月 9 日的判断）：密钥配置有问题。需要修改服务器端的 authorized_keys 或 sshd_config。

**正确的排查姿态**：不要假设问题出在哪一层。从最底层开始，逐层验证，让证据说话。

### 3.2 逐层排查实录

#### Step 1: 服务器 sshd 在运行吗？

```powershell
Get-Service sshd
# Status: Running ✅
```
如果这里就失败了（Stopped），后续全部白费。先确认服务活着。

#### Step 2: 端口在监听吗？

```powershell
netstat -an | findstr ":22 "
# 0.0.0.0:22 LISTENING ✅
```
端口没开 → 防火墙/服务配置问题。端口开了 → 继续。

#### Step 3: 防火墙放行了吗？

```powershell
netsh advfirewall firewall show rule name=all dir=in | findstr -i ssh
# 规则名称: OpenSSH SSH Server (sshd) ✅
```
这是 Windows 上容易遗漏的一步。Linux 用 `iptables` / `ufw`。

#### Step 4: 用户权限对吗？

```powershell
whoami /groups
# 无 Administrators 组 ✅
```
Windows OpenSSH 的特殊规则：管理员组用户的 authorized_keys 被忽略，改用 `administrators_authorized_keys`。这个坑浪费了大量时间。

#### Step 5: 密钥在服务器上吗？

```powershell
ssh-keygen -lf C:\Users\AIPatho1\.ssh\authorized_keys
# SHA256:YyuinNofXZIvOFnfXzRtqELATd+pwlZiixCfkzusE00 ✅
```
用 `ssh-keygen -lf` 而不是直接 `type` 来看——它能解析密钥的指纹，不受行尾/编码影响。

#### Step 6: 文件格式对吗？（本次发现的问题）

```powershell
Format-Hex C:\Users\AIPatho1\.ssh\authorized_keys
# Offset 0x6E: 0A (LF) ← 无 0D (CR)
# Offset 0x00: 73 73 68  ← "ssh"，无 BOM
```

⚠️ **发现了 CRLF 行尾**。Windows 编辑器默认用 `\r\n`。Microsoft 官方 OpenSSH 文档未强制规定行尾格式，但统一为 LF 是合理加固——`\r` 可能被误当作密钥数据导致解析异常。**本次 CRLF 不是认证失败的根因**（SSH 包根本没到正确的 sshd），但修复它消除了潜在二次问题。

**教训**：在 Windows 服务器上编辑 `authorized_keys`，永远用这条命令写入：
```powershell
$content = $content -replace "`r`n", "`n"
[System.IO.File]::WriteAllText('路径', $content)
```

#### Step 7: 权限链正确吗？（本次发现的问题）

```powershell
icacls C:\Users\AIPatho1
# ... LZD:(OI)(CI)(F)  ← 第三方用户有 FullControl！
```

Windows OpenSSH 的 `StrictModes`（默认开启）检查从家目录→`.ssh`→`authorized_keys` 的**整个路径链**的权限。任何非特权用户（非 SYSTEM/Administrators/所有者本人）有写权限 → sshd 认定文件不安全 → **拒绝信任全部密钥**。

这就是为什么日志里完全没有 AIPatho1 的连接记录——sshd 在权限检查阶段就拒绝了，没走到密钥匹配那一步。

**教训**：`icacls` 不只查文件本身，要查整条路径。

#### Step 8: TCP 能通吗？（客户端检查）

```powershell
Test-NetConnection -ComputerName 117.68.10.96 -Port 22
# TcpTestSucceeded: True ✅
```
TCP 22 端口可达。如果 False，问题在 ISP 防火墙或 NAT。中国家庭宽带常封锁入站 22 端口。

#### Step 9: SSH 协议能握手吗？（客户端检查）

```bash
ssh -vvv AIPatho1@117.68.10.96
# Remote protocol version 2.0, remote software version OpenSSH_8.7
# Server host key: ssh-ed25519 SHA256:KBbosTzX56hI2npr9vmhGblyW4hPViiQsH19FQayB80
# Authentications that can continue: publickey,gssapi-keyex,gssapi-with-mic
# Permission denied (publickey,gssapi-keyex,gssapi-with-mic).
```

`-vvv` 是排障最关键的工具。这里透露了三个关键信息：
1. 远程运行的是 OpenSSH 8.7（是 Windows 的 sshd）
2. Host Key 指纹（这是决定性线索）
3. 认证方法列表（只有 publickey 和 gssapi，**无 password**）

#### Step 10: 🔴 关键突破——Host Key 比对

在服务器本机运行：
```powershell
ssh localhost
# Host Key: SHA256:9Pc4n2V+7eaPoTzaov5m5gzMzuwyFCO2zBtaQyGb+Yk
```

| 来源 | Host Key |
|------|----------|
| `117.68.10.96:22` | `SHA256:KBbosTzX56...` |
| `localhost:22` | `SHA256:9Pc4n2V+7ea...` |

**不同！** 这意味着公网 117.68.10.96:22 和本机 localhost:22 是两个不同的 sshd → 是两台不同的机器。

#### Step 11: 最终验证

```powershell
# 服务器日志中没有任何 AIPatho1 的连接记录
wevtutil qe "OpenSSH/Operational" /c:30 /rd:true /f:text
# 只有内网 10.158.202.26 的攻击记录 → 我们的包从未到达这台机器的 sshd

# 本机 IP 确认
ipconfig | findstr "IPv4"
# 10.192.41.155
# 公网 117.68.10.96 通过 NAT 转发 → 22 端口未转发到 10.192.41.155
```

### 3.3 根因

```
117.68.10.96:22  ──NAT──→ 另一台 Windows 机器（Host Key: KBbos...）
                          ❌ 不是 DESKTOP-HKP0IV0 (Host Key: 9Pc4n2V...)
                          ❌ 那台机器上没有 AIPatho1 账户和相关密钥
```

**服务器的 SSH 配置（sshd/密钥/权限/用户组）全部正确。** 我们把正确的钥匙插入了错误的门。

## 四、AI Agent 如何操作远程服务器

### 4.1 为什么要让 AI Agent 操作服务器？

```
传统工作流（当前）：
  你在本地写代码 → 推送到 Gitee → RDP 登录服务器 → git pull → 手动敲命令训练
  训练完成后 → RDP 登录 → 查看结果 → 手动复制回本地

AI Agent 工作流（SSH 打通后）：
  你告诉 Claude Code："训练 Fold1 LoRA r=8"
  → AI 自动 push 代码 → SSH 远程执行训练命令 → 监控进度 → 回收结果 → 生成报告
```

### 4.2 原理

AI Agent（Claude Code）通过 Bash 工具执行命令。SSH 提供了一个远程 Shell，Bash 工具可以像执行本地命令一样执行远程命令：

```bash
# 本地命令
python train.py --epochs 50

# 远程命令（对外壳透明）
ssh pfmval_server "python train.py --epochs 50"

# AI Agent 看来完全一样——都是 Bash 工具的一个调用
```

### 4.3 三种连接模式

```
模式 1: 远程执行（推荐用于训练启动）
┌──────────────────────────────────────────────────────────────┐
│ ssh pfmval_server "python train.py --epochs 50"             │
│ 优点：简单，一条命令                                         │
│ 缺点：训练结束前 SSH 不能断开（需配合 nohup/screen）          │
└──────────────────────────────────────────────────────────────┘

模式 2: 交互式会话（推荐用于调试）
┌──────────────────────────────────────────────────────────────┐
│ ssh pfmval_server                                           │
│ > python train.py --epochs 50                               │
│ > # 可以交互式查看输出                                       │
│ 缺点：AI Agent 不适合长时间维持交互会话                       │
└──────────────────────────────────────────────────────────────┘

模式 3: 文件传输 + 远程执行（推荐用于完整工作流）
┌──────────────────────────────────────────────────────────────┐
│ # 上传脚本                                                   │
│ scp deploy/run.sh pfmval_server:D:/deploy/                   │
│ # 远程执行                                                   │
│ ssh pfmval_server "bash D:/deploy/run.sh"                   │
│ # 回收结果                                                   │
│ scp -r pfmval_server:D:/checkpoints/ ./results/             │
└──────────────────────────────────────────────────────────────┘
```

### 4.4 防中断机制

长时间训练需要保证 SSH 断开不影响进程：

#### Linux 服务器

```bash
# screen（最常用）
ssh pfmval_server "screen -dmS fold1 python train.py --epochs 50"
# 查看进度：ssh pfmval_server "screen -r fold1"

# tmux
ssh pfmval_server "tmux new -d -s fold1 'python train.py --epochs 50'"

# nohup
ssh pfmval_server "nohup python train.py > train.log 2>&1 &"
```

#### Windows 服务器（我们的情况）

```powershell
# 方式 1：Start-Process 后台启动
ssh pfmval_server 'Start-Process -NoNewWindow python -ArgumentList "train.py --epochs 50"'

# 方式 2：schtasks 计划任务（最可靠）
ssh pfmval_server 'schtasks /create /tn "fold1_training" /tr "python train.py" /sc once /st 00:00 /f; schtasks /run /tn "fold1_training"'

# 方式 3：使用 cmd /c start
ssh pfmval_server 'cmd /c "start /b python train.py --epochs 50 > train.log 2>&1"'
```

### 4.5 SSH Config 简化连接

`~/.ssh/config` 文件让你用简短别名代替长命令：

```
Host pfmval_server
    HostName 117.68.10.96
    User AIPatho1
    Port 22022                                    # 待管理员开放
    IdentityFile ~/.ssh/pfmval_server
    IdentitiesOnly yes
    ServerAliveInterval 60                        # 每 60 秒发送心跳防超时断开
    ServerAliveCountMax 5                         # 5 次心跳失败才断开
    StrictHostKeyChecking accept-new              # 自动接受新 Host Key（AI Agent 需要）
    UserKnownHostsFile ~/.ssh/known_hosts
    ConnectTimeout 10
    LogLevel ERROR                                # 减少日志噪音（AI Agent 需要干净输出）
```

配置后：
```bash
# 之前
ssh -i ~/.ssh/pfmval_server -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new AIPatho1@117.68.10.96 -p 22022 "python train.py"

# 之后
ssh pfmval_server "python train.py"
```

## 五、排障检查清单（可复用模板）

当你需要在**任何**新服务器上配置 SSH 连接时，按此清单逐项排查：

### 服务器端（RDP/物理登录后执行）

```markdown
☐ 1. sshd 是否运行？                    → Get-Service sshd | systemctl status sshd
☐ 2. 端口是否监听？                      → netstat -an | ss -tlnp
☐ 3. 防火墙是否放行？                    → firewall-cmd | ufw | Windows 防火墙
☐ 4. 用户是否在管理员组？                → whoami /groups | groups
☐ 5. authorized_keys 是否存在？          → ~/.ssh/authorized_keys
☐ 6. 密钥指纹是否匹配？                  → ssh-keygen -lf ~/.ssh/authorized_keys
☐ 7. 文件是否有 BOM？                    → Format-Hex | xxd
☐ 8. 行尾是否为 LF？                     → Format-Hex | file
☐ 9. ~/.ssh 目录权限？                   → icacls | ls -la
☐ 10. authorized_keys 权限？              → icacls | ls -la
☐ 11. 家目录权限？                        → icacls ~ | ls -la ~
☐ 12. sshd_config 是否有冲突配置？        → Match/DenyUsers/AllowUsers
☐ 13. 本机 localhost SSH 是否通？          → ssh localhost
☐ 14. IP 地址确认？                       → ipconfig | ip addr
☐ 15. SSH 日志有无认证记录？              → wevtutil | journalctl
```

### 客户端（本地执行）

```markdown
☐ 1. TCP 端口是否可达？                  → Test-NetConnection | nc -zv
☐ 2. 路由是否可达？                      → tracert | traceroute
☐ 3. SSH 协议能否握手？                  → ssh -vvv
☐ 4. Host Key 是否匹配？                 → 与服务器本地的 Host Key 比对
☐ 5. 认证方法列表是否包含 publickey？     → ssh -vvv 输出中查看
☐ 6. 密钥指纹是否与服务器匹配？           → ssh-keygen -lf ~/.ssh/key.pub
☐ 7. ~/.ssh/config 有无冲突配置？         → cat ~/.ssh/config
☐ 8. ssh-agent 是否干扰？                → ssh-add -l
```

## 六、关键教训与铁律

### 6.1 排障铁律

1. **永远从底层往上层查**。先确认 SSH 服务在运行，再查端口，再查网络，最后查密钥
2. **用 `-vvv` 获取完整信息**。`Permission denied` 只是一个症状，`-vvv` 告诉你哪一步失败了
3. **比对 Host Key**。当怀疑端口映射问题时，Host Key 是最可靠的指纹
4. **查日志不只查文件**。日志里**没有**你的连接记录，和日志里有错误记录，同样重要
5. **不要假设问题在哪**。6 月 9 日我们假设是密钥配置问题，花了两天检查配置。实际问题是端口映射

### 6.2 Windows SSH 特殊坑点

| 坑 | 现象 | 解法 |
|----|------|------|
| CRLF 行尾 | 密钥正确但解析可能异常（非必然） | 统一为 LF：`-replace "\`r\`n", "\`n"`（加固措施，非强制） |
| Administrators 组 | authorized_keys 被忽略 | 用 `administrators_authorized_keys` 或移出管理员组 |
| StrictModes 权限链 | 任何路径节点的第三方写权限会导致拒绝 | 整条权限链审计 |
| 日志权限 | 安全日志需提权 | 只用 Operational/Admin 日志 |
| 公网 NAT | Host Key 不匹配 | 比对 localhost 和公网的 Host Key |

### 6.3 可迁移知识点

无论你以后连接什么操作系统的服务器（Linux/macOS/Windows），这套排查方法论通用：

```
1. 确认服务在运行
2. 确认端口在监听
3. 确认防火墙放行
4. 确认网络可达
5. 确认协议能握手
6. 确认 Host Key 正确
7. 确认密钥在正确位置
8. 确认文件格式正确
9. 确认权限正确
10. 看日志找具体错误
```
