- 建议先掌握：source commit 是运行时实现身份，不等于最终分支 HEAD。

## 1. 这次修复真正要回答什么

不是“如何让 JSON 校验通过”，而是“如何不改变历史事实地表达一个预注册四臂实验”。四臂共享协议，但实际运行 attempt、source 和 return commit 不完全相同；正确 importer 必须同时保存共享关系和差异。

## 2. 必要前置知识

- quarantine：隔离区。文件可被读取和验证，但不能成为 accepted 证据。
- result envelope：结果信封。把结果、来源、作业、指标和 artifact 绑定到同一个机器可验证对象。
- atomic import：原子导入。全部写入成功才生效；任何一步失败都恢复原状态。
- provenance：来源链。记录结果由哪个协议、attempt、source commit 和 return commit 产生。
- PCC：Pearson correlation coefficient，皮尔逊相关系数，越高代表线性相关更强。
- R²：coefficient of determination，决定系数；外部 R² 为负说明相对该外部样本的均值预测基准仍较差。

## 3. 当前 importer 为什么不适配

现有 `result import` 假设一个 bundle 有一个 `result.json`、一个 job、一个 source、一个 result_id。W007 的输入是四个 `return_manifest.json`：FBR 是基线复放，另外三臂是独立训练；它们的 source 还经历了受治理的分段更新。因此，简单改名或拼接 JSON 会丢失绑定，不能视为合规转换。

## 4. 为什么建议原子 result set

W007 的科学问题是四臂同时比较。把四臂事后拆成四个实验，会让共享的 seed、split、冻结顺序和 XZY 反馈禁区变得隐含；逐次写入一个 experiment 的单一 result 字段，又会使后一次覆盖前一次。原子 result set 可在一个事务中保存四臂，并要求“缺一臂则不接纳”。

## 5. 为什么逐 arm source 更忠实

source commit 回答“这一臂实际由哪版代码生成”。最终分支 HEAD 回答“工作树后来走到了哪里”。两者不能互换。逐 arm 记录 `source_commit + attempt_id + return_commit`，才能解释 FBR/RCC/HCR/CPGCR 的真实执行差异，同时由顶层 protocol revision 说明它们属于同一预注册实验。

## 6. 每个实施步骤为何这样设计

### RPC-1 Return Profile Contract（回传画像合同）

#### 为什么需要

先定义机器可表达的事实，避免 importer 通过特例代码暗中改变科学语义。

#### 本项目修改

从单 result 改为一个 result set 下四个 arm result，并显式区分 FBR replay 与三次训练。

#### 风险与用户决策

schema 过度通用会扩大维护面；建议只做满足 W007 和未来同类预注册多臂批次的最小字段。

### HSR-2 Historical State Replay（历史状态重放）

#### 为什么需要

main 的 W007 状态停在 preflight，不能直接导入 formal 结果。

#### 本项目修改

从“复制 W007 分支 JSON”改为“CLI 按事件幂等重放”。这样 main 的其他新状态不会被旧分支覆盖。

#### 风险与用户决策

若重放接口缺失，应先补接口和测试；不得手工改 Registry。

### QSV-3 Quarantine Set Validation（隔离结果集验证）

#### 为什么需要

文件存在不等于结果有效。必须确认样本、truth、指标和来源闭包。

#### 本项目修改

除库存/大小/Git 树外，加入跨臂相同 ID/truth 和原始预测重算指标；不扩大普通文件哈希治理。

#### 风险与用户决策

普通 TXT 是否必须补回由 KDP-3 决定；原始预测、metrics 和 source 不能豁免。

### ARSI-4 Atomic Result-Set Import（原子结果集导入）

#### 为什么需要

避免四次导入只完成一部分，或后一个 result 覆盖前一个。

#### 本项目修改

写前 preview、写中事务、写后严格状态验证；重复导入必须幂等。

#### 风险与用户决策

事务实现错误可能污染状态包，因此必须有故障注入与回滚测试。

### PCP-5 Pending Conclusion Projection（待审结论投影）

#### 为什么需要

机器验证结果与用户批准结论是两道门。

#### 本项目修改

先记录 pending_review；用户批准后才接受“无明确优胜者”的稳定表述。

#### 风险与用户决策

不得把 HCR 的 PCC 或 CPGCR 的 MAE/R² 单项最好自动转成 winner。

### MGV-6 Minimal Governance Verification（最小治理验证）

#### 为什么需要

修复的是导入合同，不是模型；测试应集中于状态、绑定、事务和幂等。

#### 本项目修改

只运行治理单测和严格门禁，不运行新训练或 XZY 重评估。

#### 风险与用户决策

若最小测试暴露公共 importer 回归，停止实施并回退修复提交。

## 7. 指标与结果解读

W007 的内部选择指标是 patient-balanced z-MSE，外部 XZY 不能选择 checkpoint。HCR external PCC 略高、CPGCR external raw MAE/R² 略好、RCC internal z-MSE 最低，这是“方向混合”，不是三个可随意挑选的胜者标准。单 seed 无法估计训练随机性的稳定性。

## 8. 外部评估与防泄漏

XZY 结果只允许在四臂配置和 checkpoint 冻结后查看。importer 应存储 `external_may_select=false`，并禁止由 external 指标生成 rerun 或 config revision。

## 9. 后续升级触发条件

只有用户先审核本部署方案，再批准独立实施方案，才能修改治理代码。多 seed、重跑、补实验臂或按 XZY 调参均不属于本修复范围，必须另行立项。

## 10. 常见疑问

**能否把四个 return commit cherry-pick 到 main？** 不能。它们是结果载荷，应留在 quarantine/import 流程。

**能否直接编辑 Registry 填入指标？** 不能。这样缺少 job/source/attempt 与事务验证。

**负 R² 是否表示模型完全无用？** 不等同。它表示在该 external 数据和逐通路 raw R² 定义下，平均表现未超过以真实均值为基准的常数预测；PCC 仍可为正，因此需同时报告相关性和误差。
