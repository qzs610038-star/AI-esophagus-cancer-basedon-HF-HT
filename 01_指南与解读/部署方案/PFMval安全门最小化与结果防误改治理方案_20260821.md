# PFMval 安全门最小化与结果防误改治理方案

> 状态：待用户修改与审核  
> 版本：v0.1  
> 日期：2026-08-21  
> 性质：治理部署方案讨论稿  
> 当前授权边界：仅落盘方案；不授权修改治理代码、Registry、服务器路径、实验协议或结果，不授权训练、派发、导入、接纳、提交或远端推送。

## 1. 背景与问题

当前项目使用统一的 `agent start-check --strict` 同时检查实验工作树、机器状态、文档 Registry、学习指南、生成视图、服务器路径、工作流目录和结果状态。该设计覆盖面较大，但给日常实验开发带来以下问题：

1. 工作树绑定后，来源部署方案可能仍为本地文件，未随 Git 进入工作树；如果安全门或模型上下文继续依赖该文件，可能出现缺失、误报或上下文不完整。
2. 文档、报告、Dashboard、README、PROJECT_GUIDE 等知识层或派生内容的漂移，会干扰本来只需要确认工作树身份的代码开发。
3. 多数检查在每次代码编辑前重复运行，但真正影响实验安全的状态只在工作树绑定、训练派发和结果导入三个事件点发生变化。
4. 用户不会手工编辑结果文件；本轮最低安全目标应聚焦于防止 Agent 意外修改服务器回传的关键结果文件。

本方案采用“保留旧全量门禁但退出日常热路径”的方式实现最小改造，不删除旧能力，不迁移历史资料，也不新建报告体系。

## 2. 目标

### 2.1 必须实现

1. 工作树内具有自包含、受 Git 跟踪、经过用户审核的实验执行上下文。
2. 日常代码开发不再检查无关文档、报告、生成视图和服务器状态。
3. 正式训练派发只检查当前 job 实际依赖的身份、批准、合同、路径和输入。
4. 结果导入能够发现 Agent 对关键回传文件的任何意外修改。
5. 普通日志、说明文件和诊断材料不新增 SHA-256 校验。
6. 文档生命周期由用户周期性复核，不阻塞实验开发和派发。

### 2.2 不在本轮实施

- 不迁移或清理历史文档。
- 不删除现有 `validate_state()`、`--strict` 或兼容入口。
- 不重建 `document_registry.json` schema。
- 不修改历史结果、历史实施方案或实验结论。
- 不修改服务器路径、训练协议或受保护资产。
- 不引入服务器签名、Gitee 受保护分支或新的密钥系统。
- 不生成新的 Markdown 审计报告。

## 3. 最小安全标准

本方案将最低安全标准定义为：

1. Agent 在普通代码开发期间不能进入错误的 W###、分支或 experiment。
2. 未绑定 source commit、job、attempt、protocol revision 和用户批准时不能派发正式训练。
3. 服务器回传的关键结果字节发生变化时，导入必须失败且不得写入 Registry。
4. supporting 或 diagnostic 文件不得作为正式指标来源。
5. 任一验证失败均不得产生部分状态写入。

该标准防止意外操作和误导入。它不试图防范拥有仓库写权限并主动伪造完整提交链的恶意 Agent；若未来需要这一威胁模型，必须另行引入服务器签名或受保护分支。

## 4. 实施方案

### CA1 上下文权威收敛（Context Authority）

#### 4.1 权威执行上下文

工作树内的实验执行依据收敛为：

1. `project_state/implementation_plans/W###-<工作树名>_实施方案.md`；
2. `experiments/experiment_registry.json` 中对应 experiment；
3. `project_state/workspace_registry.json` 中对应 W###；
4. experiment 对应的机器可读 critical contract。

来源部署方案继续允许保留为本地讨论与追溯材料，不要求进入 Git，也不要求在 W### 工作树中存在。来源部署方案缺失不得单独造成 development 或 dispatch 门失败。

#### 4.2 实施方案自包含字段

实施方案必须受 Git 跟踪，并至少包含：

- 来源部署方案路径与 revision，仅用于追溯；
- 用户批准指令 ID；
- `workspace_id`；
- `experiment_id`；
- `protocol_revision`；
- 代码目录与配置文件；
- 修改前配置；
- 分步任务；
- 停止条件；
- 关键输入合同；
- 原始预测与训练记录回传要求；
- 当前进度、commit、测试和证据位置。

实施方案经过用户第二次审核后，成为该工作树的自包含执行上下文。工作树内不再反向读取大量部署报告补齐执行信息。

#### 4.3 预计修改

- `AGENTS.md`
- `project_state/implementation_plans/README.md`

不修改 `.gitignore`，避免把整个部署方案目录同步到所有工作树。

### LG2 轻量开发门（Lightweight Gate）

#### 4.4 新入口

```powershell
python deploy/pfmval_ops.py agent start-check `
  --task development `
  --workspace W007
```

#### 4.5 HARD 检查

development 门只检查：

1. 当前目录是指定 W### 登记的本地 Git worktree；
2. 当前分支等于 Registry 登记分支；
3. 当前 HEAD 是 Registry 登记基线提交的后代；
4. W### 未处于 `close_ready`、`tombstoned`、`archived` 或其他不可执行状态；
5. W### 与 experiment 唯一绑定；
6. 对应实施方案存在且受 Git 跟踪；
7. 不存在未完成状态事务或状态锁。

工作区存在未提交代码属于正常开发状态，不得阻塞 development 门。

#### 4.6 明确移除的日常检查

development 门不检查：

- `document_registry.json` 新鲜度；
- 来源部署方案原文件；
- 学习指南、分析报告或会议材料；
- Dashboard、README、PROJECT_GUIDE、CURRENT_STATE.md；
- 无关工作树；
- workflow catalog；
- 无关服务器路径；
- 文档内容 SHA-256；
- 当前开发 HEAD 是否严格等于登记基线提交。

#### 4.7 实现方式

在 `scripts/pfmval_state.py` 新增独立的 `validate_development_context()`。不要重写现有大型 `validate_state()`，以便旧全量门禁继续用于显式治理审计。

在 `deploy/pfmval_ops.py` 中：

- 为 `agent start-check --task` 增加 `development`；
- 增加 `--workspace W###`；
- 将 development 路由到新验证函数。

### EG3 执行事件门（Execution Gate）

#### 4.8 新入口

```powershell
python deploy/pfmval_ops.py agent start-check `
  --task dispatch `
  --workspace W007 `
  --job-id <JOB_ID>
```

#### 4.9 HARD 检查

dispatch 门在 development 门基础上增加：

1. Git 工作区 clean；
2. 当前 HEAD 等于 job 的 `source_commit`；
3. job、attempt、experiment、workspace 和 protocol revision 相互匹配；
4. 正式训练具有当前、有效、范围匹配的用户批准；
5. critical contract 与 job 绑定一致；
6. attempt lease 与 run budget 有效；
7. 传输方式为 Gitee-only；
8. 只检查 job 实际引用的服务器 path id；
9. 只验证 job 实际引用的关键输入资产。

dispatch 门不得扫描全部服务器路径、全部历史 approval/event、全部文档或全部无关工作树。

#### 4.10 训练入口切换

将 `deploy/run_experiment.ps1` 中的：

```powershell
agent start-check --strict --task training
```

替换为 dispatch 门。

旧 `--strict` 保留，仅用于：

- 显式治理审计；
- Registry 结构升级；
- 受保护资产重新生成；
- 正式结果接纳独立审计；
- 用户明确要求的全项目核验。

### RI4 结果完整性保护（Result Integrity）

#### 4.11 统一新实验结果入口

新实验结果统一使用现有 `result-bundle-v1`，不再使用面向新实验的通用本地 `result import --bundle` 入口。

```powershell
python deploy/pfmval_ops.py governance result-bundle-v1 record-import `
  --bundle <GITEE_RETURN_BUNDLE> `
  --bundle-sha256 <SERVER_PUBLISH_RECEIPT_SHA256>
```

#### 4.12 必须保留的关键检查

- `workspace_id`；
- `experiment_id`；
- `job_id`；
- `attempt_id`；
- `source_commit`；
- `protocol_revision`；
- `critical_contract_sha256`；
- terminal JSON；
- 每个已评估 split 的原始预测；
- 必需的原始训练 CSV/TXT；
- 结果包 Git 文件树闭包；
- 关键文件 SHA-256。

#### 4.13 文件分层

| evidence role | 用途 | 完整性检查 | 能否作为正式指标来源 |
|---|---|---|---|
| `critical` | 合同、terminal、原始预测、正式指标来源 | SHA-256 + 大小 + Git 闭包 | 可以 |
| `supporting` | 普通日志与辅助说明 | 清单 + 大小 + Git 闭包 | 不可以 |
| `diagnostic` | 排障信息 | 清单 + 大小 + Git 闭包 | 不可以 |

#### 4.14 Agent 防误改规则

1. Agent 禁止编辑 Gitee 返回目录、`result.json`、terminal、预测表和训练记录。
2. `bundle_sha256` 必须来自服务器发布回执，禁止 Agent根据本地下载后的文件重新生成“期望值”。
3. 导入器重新计算本地关键结果包身份，并与服务器回执对比。
4. 任一关键文件被修改后，导入必须失败。
5. 验证失败不得更新 experiment Registry、current state 或 accepted evidence。

本轮不增加新的通用指标重算器。该门保证结果字节与服务器发布包一致；科学指标计算逻辑的独立复算如有需要，应另开任务。

### DR5 周期文档复核（Document Review）

#### 4.15 周期与入口

文档治理改为建议每周一次的人工复核，不参与 development、dispatch 或结果导入门禁。

```powershell
python deploy/pfmval_ops.py knowledge profile `
  --profile lifecycle_review
```

终端只显示：

- 当前 active 文档；
- 新发现文档；
- 缺失文档；
- 建议归档文档；
- active scope 冲突。

#### 4.16 用户决策

用户明确选择后，才运行现有生命周期命令：

```powershell
python deploy/pfmval_ops.py docs set-lifecycle `
  --doc-id <DOC_ID> `
  --lifecycle historical
```

固定边界：

- 未执行周检不阻塞实验；
- 不自动归档；
- 不自动生成 Markdown 报告；
- 文档内容不参与日常 SHA-256 校验；
- document Registry 只用于模型上下文路由，不作为实验真实性证据。

### VT6 最简验收测试（Verification Tests）

#### 4.17 development 门测试

1. 工作树缺少来源部署方案，但有 tracked 实施方案：PASS。
2. 工作区 dirty：PASS。
3. 分支错误：FAIL。
4. W### 与 experiment 不匹配：FAIL。
5. HEAD 不是登记提交后代：FAIL。
6. 实施方案未跟踪或缺失：FAIL。
7. Dashboard、学习指南或文档 Registry 过期：不影响结果。

#### 4.18 dispatch 门测试

1. clean HEAD、job、approval、attempt、contract 一致：PASS。
2. source commit 不一致：FAIL。
3. 正式批准缺失：FAIL。
4. Gitee-only 被改变：FAIL。
5. 无关服务器路径缺失：不影响结果。

#### 4.19 结果门测试

1. 修改原始预测一个字节：FAIL。
2. 修改 terminal JSON：FAIL。
3. 修改 `result.json`：FAIL。
4. 使用错误的服务器回执 bundle SHA：FAIL。
5. supporting 或 diagnostic 文件不能成为正式指标来源。
6. 验证失败后 Registry 和 current state 不发生写入。

#### 4.20 最简测试命令

```powershell
python -m pytest `
  tests/test_pfmval_state.py `
  tests/test_result_bundle_v1.py `
  -k "development or dispatch or tampering or supporting or record_import"
```

不要求运行与本次治理改造无关的模型、训练或全项目测试。

## 6. 哈希治理边界

### 6.1 建议保留

仅继续使用现有 SHA-256 校验：

- 关键输入合同；
- terminal；
- 原始预测；
- 正式指标来源；
- 关键结果包闭包。

### 6.2 明确取消或不新增

- 部署方案；
- 实施说明文字；
- 学习指南；
- 分析报告；
- 普通日志；
- diagnostic 文件；
- supporting 文件。

### 6.3 必要性与负面影响

必要性：如果没有独立的服务器回执 SHA，Agent 修改关键文件并同步修改本地 manifest 后，导入器无法识别原始服务器发布包已经变化。

负面影响：

- 导入关键结果时增加一次文件读取；
- 关键结果发生变化时需要重新回传；
- 不影响训练速度；
- 不对普通日志和文档计算哈希。

该哈希边界必须在实施前获得用户明确批准；本讨论稿本身不构成授权。

## 7. 实施顺序与停止点

1. CA1：先更新执行上下文规则与实施方案模板。
2. LG2：实现 development 门并完成专项测试。
3. EG3：实现 dispatch 门，确认后再切换训练入口。
4. RI4：固化新实验结果只走 `result-bundle-v1` 的规则。
5. DR5：将文档检查移出日常门禁并保留人工周期复核。
6. VT6：运行最简测试并提交用户审核。

任一步出现以下情况必须停止：

- development 或 dispatch 错误放行错误工作树；
- 正式训练能够绕过批准；
- 关键结果文件被修改后仍可导入；
- 验证失败产生 Registry 部分写入；
- 修改范围扩展到服务器路径、实验协议、历史结果或受保护资产。

## 8. 验收标准

本方案实施完成需同时满足：

1. W### 不包含来源部署方案时，代码开发仍可获得完整、可靠的自包含上下文。
2. 文档、报告或生成视图过期不阻塞 development 和 dispatch。
3. 错误工作树、分支、experiment 或 source commit 必须阻塞。
4. 无正式批准不能派发正式训练。
5. 修改任一 critical 结果文件后导入失败，且状态文件零写入。
6. supporting/diagnostic 文件不新增哈希，也不能成为正式指标来源。
7. 旧 full strict 仍可供显式治理审计使用。
