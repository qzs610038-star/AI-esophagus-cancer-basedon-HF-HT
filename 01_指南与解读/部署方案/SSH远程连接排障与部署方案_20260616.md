## 二、完整排查记录

### 排查方法论

采用 **OSI 七层自底向上**的排查策略：

```
Layer 1-2 (物理/链路):  网线/网卡是否工作        → 跳过（RDP 通，物理层正常）
Layer 3 (网络层/IP):    路由是否可达              → tracert + Test-NetConnection
Layer 4 (传输层/TCP):   端口是否开放              → Test-NetConnection -Port 22
Layer 5-6 (会话/表示):  SSH 协议握手              → ssh -vvv（版本协商/KEX）
Layer 7 (应用层/SSH):    密钥认证                  → authorized_keys / 权限 / 文件格式
```

### Phase 1: 服务器端自查（通过 RDP 在服务器本地执行）

#### 1.1 sshd 服务状态

```powershell
Get-Service sshd
# Name: sshd | Status: Running | StartType: Automatic
```
✅ sshd 正在运行，开机自启。

#### 1.2 端口监听

```powershell
netstat -an | findstr ":22 "
# TCP  0.0.0.0:22  0.0.0.0:0  LISTENING
# TCP  [::]:22      [::]:0     LISTENING
```
✅ 双栈监听（IPv4 + IPv6）。

#### 1.3 防火墙规则

```powershell
netsh advfirewall firewall show rule name=all dir=in | findstr -i ssh
# 规则名称: OpenSSH SSH Server (sshd)
# 分组:     OpenSSH Server
```
✅ 防火墙入站规则存在。

#### 1.4 用户组确认

```powershell
whoami /groups
# Everyone, BUILTIN\Remote Desktop Users, BUILTIN\Users, ...
# 无 S-1-5-32-544 (Administrators)
```
✅ AIPatho1 不在管理员组 → 不触发 `Match Group administrators` 规则 → 使用用户级 `authorized_keys`。

#### 1.5 authorized_keys 内容

```powershell
ssh-keygen -lf C:\Users\AIPatho1\.ssh\authorized_keys
# 5 把 ed25519 密钥（排查前），指纹均与本地公钥匹配
```
✅ 密钥存在且指纹匹配。

#### 1.6 文件格式检查

```powershell
# Hex 分析
# Offset 0x6E: 0A (LF)  → 无 CR (0x0D)
# Offset 0x00: 73 73 68 → "ssh"，无 BOM (EF BB BF)
```
⚠️ **发现 authorized_keys 存在 CRLF 行尾**（Windows 编辑器默认行为）。Microsoft 官方 OpenSSH 文档确认普通用户的 authorized_keys 路径为 `%USERPROFILE%\.ssh\authorized_keys`，但未明确约束行尾格式。实际测试表明 OpenSSH 对行尾格式有容忍度，因此 **统一为 LF/无 BOM 是合理加固，但本次未证明 CRLF 是直接原因**。已通过 PowerShell 修复：
```powershell
$content = Get-Content 'authorized_keys' -Raw
$content = $content -replace "`r`n", "`n"
[System.IO.File]::WriteAllText('authorized_keys', $content)
```

#### 1.7 权限链审计

```powershell
# .ssh 目录
icacls C:\Users\AIPatho1\.ssh
# NT AUTHORITY\SYSTEM:(F)  DESKTOP-HKP0IV0\AIPatho1:(F)
# 无继承 (IsInherited: False)，无第三方

# authorized_keys
icacls C:\Users\AIPatho1\.ssh\authorized_keys
# 同上，权限正确

# 家目录
icacls C:\Users\AIPatho1
# SYSTEM:(OI)(CI)(F)  Administrators:(OI)(CI)(F)
# AIPatho1:(OI)(CI)(F)  ❌ LZD:(OI)(CI)(F)
```
⚠️ **发现 LZD 用户对 AIPatho1 家目录有 FullControl**。Windows OpenSSH `StrictModes`（默认 yes）检查整个路径链的权限——任何非特权用户对路径链上的节点有写权限 → 拒绝信任 `authorized_keys`。已移除。

同时打断 `.ssh` 目录的权限继承（`icacls /inheritance:d`），防止未来权限变更影响。

#### 1.8 sshd 配置审计

```powershell
type C:\ProgramData\ssh\sshd_config
```
关键配置项：
```
#Port 22                                    → 默认端口
#PubkeyAuthentication yes                   → 默认启用公钥认证
AuthorizedKeysFile .ssh/authorized_keys     → 使用用户级文件
#PasswordAuthentication yes                 → 默认启用密码
Subsystem sftp sftp-server.exe              → SFTP 已配置
Match Group administrators                  → 管理员组使用独立文件
    AuthorizedKeysFile __PROGRAMDATA__/ssh/administrators_authorized_keys
```
✅ 配置正确。`Match Group administrators` 不触发（AIPatho1 非管理员）。

#### 1.9 服务器 localhost SSH 验证

```powershell
# 密码认证测试
ssh AIPatho1@localhost "echo LOCAL_SSH_OK; hostname"
# 输入密码 → LOCAL_SSH_OK + DESKTOP-HKP0IV0
```
🟢 **服务器本地 SSH 密码认证通过**。sshd 进程与基本配置正确，但**本次仅验证了密码认证**——目标端口映射到位后，需复测公钥认证（`ssh -i ~/.ssh/pfmval_server -o IdentitiesOnly=yes`）。

## 三、根因声明

> ### **公网 IP `117.68.10.96` 的 TCP 端口 22 被 NAT 映射到另一台机器，而非 DESKTOP-HKP0IV0 (10.192.41.155)。**
>
> 服务器端 SSH **基础配置**（sshd 运行/端口监听/防火墙/用户组/authorized_keys 内容/权限链）经自查全部正确，且 **localhost 密码认证通过**。但**公钥认证尚未通过目标端口复测**——密钥认证失败的直接原因是我们的 SSH 包经由 NAT 被路由到另一台机器（Host Key 不匹配 + 服务器日志无记录）。待新端口映射到位后，需用 `ssh -p 22022 -i ~/.ssh/pfmval_server -o IdentitiesOnly=yes AIPatho1@117.68.10.96 "hostname && whoami"` 完成最终验收。

### 历史错误诊断回顾

2026-06-09 的诊断结论"密钥认证始终失败 + 网络限制"是**不完整的**：
- "密钥认证失败" — 正确现象，但当时认为是密钥配置问题
- "网络限制" — 部分正确，但当时的理解是"网络层面阻断"
- **遗漏了**：端口映射到错误机器的可能性

### 辅助发现与修复

虽然 CRLF 行尾和 LZD 权限**不是本次认证失败的直接原因**（包根本没到正确的 sshd），但它们在服务器本地 SSH 测试中被发现和修复，消除了潜在的二次问题：

| 问题 | 严重程度 | 状态 |
|------|:---:|:---:|
| authorized_keys CRLF 行尾 | 🟡 中（可能导致 sshd 解析失败） | ✅ 已修复 |
| 家目录 LZD 写权限 | 🟡 中（StrictModes 可能拒绝） | ✅ 已修复 |
| .ssh 目录权限继承 | 🟢 低（当前无影响） | ✅ 已加固 |

## 四、推荐方案

### 方案 A：新增端口映射（推荐 ⭐）

**说明**：请求管理员在路由器/NAT 上新增一条规则，**不修改现有的 22 端口映射**。

```
规则：公网 117.68.10.96 TCP 22022 → 内网 10.192.41.155 TCP 22
```

**优势**：
- 不影响现有 22 端口的 Windows 远程服务
- 一条 NAT 规则，改动最小
- 服务器端无需任何配置变更（已就绪）
- 永久生效

**劣势**：
- 依赖管理员操作（一次性）
- 如果路由器/NAT 设备有规则数量限制可能受影响

**本地连接方式**：
```bash
# 直接命令
ssh -p 22022 -i ~/.ssh/pfmval_server AIPatho1@117.68.10.96

# 或配置 ~/.ssh/config
Host pfmval_server
    HostName 117.68.10.96
    User AIPatho1
    Port 22022
    IdentityFile ~/.ssh/pfmval_server
    IdentitiesOnly yes

# 一键连接
ssh pfmval_server
```

### 方案 B：修改公网 22 NAT 映射目标（不推荐，保留备查）

**说明**：如果管理员同意将现有 `117.68.10.96:22` 的 NAT 映射目标改为 DESKTOP-HKP0IV0 (10.192.41.155:22)。

**核心限制**：同一个公网 IP 的同一个 TCP 端口**不能同时稳定指向两台内网机器**——除非路由器支持基于源 IP 的策略路由或七层反向代理（本场景几乎不可能）。这意味着改为指向本机后，原来使用 22 端口的那台机器将失去 SSH 可达性。

**优势**：使用默认端口，命令简洁

**劣势**：
- 必须修改现有映射规则（破坏性操作）
- 同一端口不能同时服务于两台机器
- 可能影响原来使用 22 端口的服务
- 不如方案 A 干净

**推荐度**：⭐（远不如方案 A）

### 方案 C：自有 VPS 反向 SSH 隧道（临时救急，非生产通道）

**说明**：利用服务器可出站的特点，通过你控制的公网 Linux/VPS 中转 SSH 流量。

```powershell
# 在服务器上运行（需保持运行）
ssh -N -R 22022:localhost:22 -o ServerAliveInterval=60 -o ExitOnForwardFailure=yes user@your_vps
```

本地连接（先连 VPS，再跳转）：
```bash
ssh -p 22022 -i ~/.ssh/pfmval_server AIPatho1@your_vps
# 或一步到位：
ssh -J user@your_vps -p 22022 -i ~/.ssh/pfmval_server AIPatho1@localhost
```

**优势**：
- 不需要管理员
- 自有 VPS 可控、可审计
- 比公共免费服务安全可靠

**劣势**：
- 需要一台公网 Linux/VPS（最低配置即可，月费约 ¥30-50）
- 隧道需要保持运行（断线后需重连）
- 额外一跳增加延迟
- **不适合长时间训练**：隧道中断 → SSH 会话断开 → 训练进程可能被终止

**⚠️ 生产训练警告**：反向隧道仅适合短命令（启动训练、检查状态、回收结果），**不要将长时间训练直接绑在隧道 SSH 会话上**。训练应通过 Windows 任务计划程序（`schtasks`）独立启动，日志落盘，通过隧道 SSH 仅用于轮询和回收。

**SSH 配置加固**（客户端 `~/.ssh/config`）：
```
Host vps_tunnel
    HostName your_vps
    User AIPatho1
    Port 22022
    IdentityFile ~/.ssh/pfmval_server
    IdentitiesOnly yes
    ServerAliveInterval 60
    ServerAliveCountMax 3
    ExitOnForwardFailure yes
```

> ⚠️ **不推荐公共免费隧道服务**（localhost.run / serveo.net / bore.pub）：依赖第三方、公网暴露 SSH 风险更高、中国大陆可用性差。如必须临时使用，至少加 `ServerAliveInterval` 和 `ExitOnForwardFailure yes`。

### 方案 D：Tailscale/ZeroTier VPN（长期网络层方案）

**说明**：在服务器和本地均安装 Tailscale/ZeroTier，建立 Mesh VPN 网络。连接方式：**用 Tailscale 建网，再连 Windows 自带 sshd**（非 Tailscale SSH 服务器功能——SSH 服务器组件目前仅支持 Linux/macOS 开源 CLI 设备）。

**优势**：
- 无需端口映射
- 加密端到端
- 不受 NAT 变化影响
- 支持多设备互联

**劣势**：
- Windows 服务器安装网络客户端**通常需要管理员权限**
- 国内访问可能受干扰（Tailscale 协调服务器在境外）
- 需注册账号

### 方案 E：VS Code Remote Tunnels（推荐 ⭐⭐ — 无管理员的首选）

> 📋 **完整实现路径已独立成文** → `VS Code Remote Tunnels远程连接部署方案_20260617.md`（含 CLI 下载、代理配置、持久化运行、AI Agent 适配、故障排查）

**说明**：通过 VS Code 官方的 Remote Tunnels 功能，服务器运行 `code tunnel` 通过出站连接到 Azure 服务建立隧道，本地通过 VS Code/网页终端连接。**不需要入站端口，不需要改 NAT，不需要防火墙改动**。

```powershell
# 服务器上（需先安装 VS Code CLI）
code tunnel
# 按提示用 GitHub/Microsoft 账号认证
# 隧道建立后输出一个 vscode.dev 链接
```

本地使用：
- VS Code 中 `Remote Explorer` → `Tunnels` → 连接
- 或直接访问输出的 `https://vscode.dev/tunnel/...` 链接，在网页中获得完整终端

**优势**：
- **不需要管理员**
- 不需要入站端口/NAT 映射
- 微软官方维护，稳定可靠
- 得到完整的远程开发环境（终端 + 文件浏览 + 编辑器）
- 自动重连

**劣势**：
- 依赖 Azure 云服务中继（国内延迟可能较高）
- 需要服务器能出站访问 `*.tunnel.dev.azure.com`
- 它是远程开发通道，不是裸 SSH（AI Agent 无法直接 `ssh` 调用，但可以通过 VS Code Remote 终端执行命令）
- 首次认证需要 GitHub/Microsoft 账号

**AI Agent 适配**：AI Agent 不能直接通过 SSH 协议调用，但如果 Claude Code 运行在连接到 tunnel 的 VS Code 窗口中，它的终端发出的命令就会在远程服务器上执行——等价于 SSH 远程操作。

### 方案 F：Cloudflare Tunnel / Access SSH（进阶，需域名配置）

**说明**：服务器运行 `cloudflared` 通过出站连接建立到 Cloudflare 边缘网络的隧道，客户端通过 `cloudflared access ssh` 接入。

```powershell
# 服务器上（一次性配置后持续运行）
cloudflared tunnel --url ssh://localhost:22
```

本地连接：
```bash
# ~/.ssh/config
Host pfmval_server
    ProxyCommand cloudflared access ssh --hostname pfmval.yourdomain.com

ssh pfmval_server
```

**优势**：
- 不需要入站端口/NAT 映射
- Cloudflare 全球网络，国内可用性较好
- 自带 Zero Trust 认证层（可加 SSO/OTP）
- 免费套餐足够使用

**劣势**：
- 需要域名 + Cloudflare 账号 + Zero Trust 配置（首次搭建复杂度较高）
- 服务器需安装 `cloudflared`
- 客户端也需要 `cloudflared`

### 方案 G：GitHub Actions Self-Hosted Runner（拉取式任务队列）

**说明**：这不是 SSH 连接，而是一种**异步任务队列**模式：在服务器上注册 GitHub Actions self-hosted runner，AI Agent 通过向私有仓库 push/dispatch 任务来触发服务器执行训练，结果自动上传为 workflow artifacts。

```
本地 AI Agent                    GitHub 私有仓库                  服务器 Runner
┌──────────┐      push/dispatch     ┌──────────┐       poll        ┌──────────┐
│ dispatch │  ─────────────────→   │  Actions  │  ←─────────────  │  runner   │
│ training │                       │  Workflow │    "有新任务?"     │ 执行训练   │
│ task     │  ←── download ─────── │ artifacts │  ── upload ──→   │ 产出结果   │
└──────────┘                       └──────────┘                  └──────────┘
```

**优势**：
- 不需要入站端口/NAT
- 服务器主动拉取任务（Pull 模式），天然穿透防火墙
- GitHub 托管基础设施，高可用
- 天然支持任务历史、日志存档、通知
- AI Agent 可用 `gh` CLI 一键 dispatch → 等待 → 下载结果

**劣势**：
- Windows runner 作为服务安装需要管理员，但 runner 本体可以下载配置后直接运行
- 仅建议用于**私有仓库**（公开仓库 runner 有恶意代码执行风险）
- 任务执行有延迟（取决于 runner 轮询间隔）
- 非实时交互——不能在训练中间介入

**AI Agent 适配**：非常适合"发训练任务 → 跑完回收结果"的批量实验场景。与 SSH 互补——SSH 用于交互式排障，Runner 用于批量任务。

### 方案 H：Windows 任务计划程序 + SSH 轮询（生产推荐 ⭐⭐⭐）

**说明**：训练不直接绑在 SSH 会话上，而是通过 `schtasks` 注册为独立后台任务，日志落盘。SSH（通过方案 A 或 E 打通后）仅用于**启动任务、轮询状态、回收结果**。

```powershell
# 注册一次性训练任务（服务器上）
schtasks /Create /TN "PFMval_CLS_LoRA_Fold1" /TR "cmd.exe /c 'set PYTHONIOENCODING=utf-8 && set HF_HUB_OFFLINE=1 && C:\Users\AIPatho1\pfmval_env\Scripts\python.exe -u D:\AIPatho\qzs\pfmval_deploy_git\train_online_cls.py --mode lora --lora_rank 8 --cross_patient --fold 1 --epochs 50 > D:\AIPatho\qzs\logs\cls_lora_fold1.log 2>&1'" /SC ONCE /ST 02:00 /F
```

本地 AI Agent 通过 SSH 交互：
```bash
# 查询任务状态
ssh pfmval_server "schtasks /Query /TN PFMval_CLS_LoRA_Fold1 /FO LIST /V"

# 查看训练日志尾部
ssh pfmval_server "Get-Content D:\AIPatho\qzs\logs\cls_lora_fold1.log -Tail 50"

# 训练完成后回收结果
scp -r pfmval_server:D:/AIPatho/qzs/pfmval_deploy_git/checkpoints/... ./results/
```

**优势**：
- 训练不会因 SSH 断开而中断
- 任务独立于任何会话，重启后仍可查询
- 可设置触发条件（特定时间、事件）
- 结合方案 A/E/F 均可用

## 八、安全加固建议

> 如果最终开放公网 SSH（方案 A / F），务必落实以下措施。以下配置均在 `C:\ProgramData\ssh\sshd_config` 中修改（需管理员编辑，改后 `Restart-Service sshd`）。

### 必须执行（P0）

```powershell
# 1. 禁用密码登录
PasswordAuthentication no

# 2. 仅允许指定用户
AllowUsers AIPatho1

# 3. 禁用 root 登录（Windows 无 root，但显式声明更安全）
PermitRootLogin no

# 4. 使用高位端口（已满足：方案 A 使用 22022）
Port 22022
```

### 强烈建议（P1）

```powershell
# 5. 客户端 keep-alive（防 SSH 会话僵死）
ClientAliveInterval 60
ClientAliveCountMax 3

# 6. 限制认证尝试次数
MaxAuthTries 3

# 7. 防火墙源 IP 白名单（如果本地 IP 固定）
New-NetFirewallRule -DisplayName "SSH_Allow_Only_Home" `
    -Direction Inbound -Protocol TCP -LocalPort 22 `
    -RemoteAddress 192.168.31.0/24 -Action Allow
# （仅示例——如本地无固定公网 IP 则跳过）
```

### 运维规范（P2）

```bash
# 8. 首次连接验证 Host Key 指纹（防止中间人攻击）
ssh-keyscan -p 22022 117.68.10.96 2>/dev/null | ssh-keygen -lf -
# 期望：SHA256:9Pc4n2V+7eaPoTzaov5m5gzMzuwyFCO2zBtaQyGb+Yk

# 9. 定期审计 authorized_keys 指纹
ssh-keygen -lf C:\Users\AIPatho1\.ssh\authorized_keys

# 10. 使用专用密钥对（不用个人日常密钥）
# 已满足：pfmval_server / pfmval_server_nopass 均为专用密钥
```

### 训练进程保护（最关键）

**长训练绝不能直接绑在 SSH 会话上！** SSH 断开 → 会话终止 → 训练进程被 kill。正确做法：

| 方式 | 命令 | 适用场景 |
|------|------|---------|
| Windows 任务计划程序 | `schtasks /Create /TN "..." /TR "..." /SC ONCE /ST HH:MM /F` | 推荐：训练独立于任何会话 |
| `Start-Process` + 日志落盘 | `Start-Process -NoNewWindow -FilePath "python" -RedirectStandardOutput "log.txt"` | 备选：简单快速 |
| SSH `nohup` 等效 | `cmd /c "start /b python train.py > log.txt 2>&1"` | 临时：仅用于短实验 |

监控模式（AI Agent 通过 SSH 轮询）：
```bash
# 检查训练进程是否存活
ssh pfmval_server "Get-Process python* -ErrorAction SilentlyContinue | Select-Object Id, CPU, WorkingSet64"

# 检查 GPU 使用
ssh pfmval_server "nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv,noheader"

# 读取最新日志
ssh pfmval_server "Get-Content D:\AIPatho\qzs\logs\train.log -Tail 30"
```
