## 二、推荐方案（按安全等级分层）

### 🟢 Tier 1 — 零风险，立即可用

这些方法**不影响数学精度**，不改变训练结果，纯收益。

#### 1.1 TF32 矩阵乘法

RTX 4080 (Ada Lovelace, SM 8.9) 的 Tensor Core 原生支持 TF32。PyTorch **仅对卷积默认开启 TF32**，矩阵乘法需手动开启：

```python
torch.backends.cuda.matmul.allow_tf32 = True  # 矩阵乘法也用 TF32
```

- **收益**：matmul 加速 1.5–2×，精度损失 ~1e-6（可忽略）
- **风险**：无。TF32 是 NVIDIA 设计的确定性格式
- **显存**：几乎不变

#### 1.2 cuDNN Auto-Tune

```python
torch.backends.cudnn.benchmark = True
```

- **收益**：卷积层 10–30% 加速（首次运行会花几秒 auto-tune，后续缓存）
- **前提**：输入 shape 固定（本项目 224×224 patch → 固定，满足条件）
- **风险**：无（仅影响 kernel 选择，不改变数值结果）
- **注意**：如果后续引入可变尺寸输入，需关闭

#### 1.3 Fused AdamW

```python
optimizer = torch.optim.AdamW(groups, weight_decay=args.weight_decay, fused=True)
```

- **收益**：优化器 step 加速 ~15–20%，减少 CPU-GPU kernel launch 开销
- **风险**：极低。PyTorch 2.0+ 官方支持，是 `torch.compile` 的推荐搭配
- **兼容性**：Windows + CUDA 11.8 均可使用

#### 1.4 DataLoader 微调

```python
train_loader = DataLoader(
    train_dataset, batch_size=args.batch_size, shuffle=True,
    num_workers=2,              # 从 0 → 2（Windows 保守值）
    pin_memory=True,
    persistent_workers=True,    # 跨 epoch 复用进程，避免 fork 开销
    prefetch_factor=4,          # 每个 worker 预取 4 个 batch（默认 2）
    drop_last=False,
)
```

- **收益**：消除数据加载瓶颈，GPU 利用率从 60% → 85%+
- **Windows 注意**：`num_workers > 0` 需要 `if __name__ == "__main__"` 保护（已有 `main()` 函数，满足条件）
- **推荐值**：服务器 `num_workers=4`，本机 `num_workers=2`（避免 NUMA 竞争）

#### 1.5 `zero_grad(set_to_none=True)`

```python
optimizer.zero_grad(set_to_none=True)
```

- **收益**：略省显存 + 略快（将梯度张量设为 None 而非填充 0）
- **风险**：无。PyTorch 官方推荐

### 🟡 Tier 2 — 极低风险，高收益（推荐优先实施）

#### 2.1 ⭐ BF16 替代 FP16（核心推荐）

RTX 4080 基于 Ada Lovelace，**原生支持 BF16 Tensor Core**。当前使用 FP16 + GradScaler 的方案在 RTX 4080 上是次优选择：

| 对比维度 | FP16 (当前) | BF16 (推荐) |
|---------|:------:|:------:|
| 指数范围 | ±65504（易溢出） | **与 FP32 相同** |
| GradScaler | ✅ 必须 | ❌ 不需要 |
| NaN/Inf 风险 | 有（需调 scale） | **几乎为零** |
| 代码复杂度 | 高（scaler 管理） | 低 |
| 精度损失 | <0.1% | <0.1% |
| 速度 | 快 | **相同或更快** |

**为什么 BF16 更安全**：BF16 用 8 位指数（与 FP32 相同），不会出现 FP16 常见的梯度下溢→零或激活溢出→Inf→NaN 的问题。你们已有的 NaN 保护（LMZ12939 极端 z-score）可以保留作为双保险。

**代码改动**（精简，移除 GradScaler）：

```python
# main() 中替换 AMP 设置
use_amp = args.amp and device.type == "cuda"
if use_amp:
    if torch.cuda.is_bf16_supported():
        amp_dtype = torch.bfloat16
        scaler = None  # BF16 不需要 GradScaler
        print("[INFO] 混合精度训练已启用 (BF16, 无需 GradScaler)")
    else:
        amp_dtype = torch.float16
        scaler = torch.amp.GradScaler('cuda')
        print("[INFO] 混合精度训练已启用 (FP16 + GradScaler)")

# train_one_epoch() 中简化
if scaler is not None:
    with torch.amp.autocast('cuda', dtype=torch.float16):
        preds = model(images, pos_x, pos_y)
        loss = criterion(preds, targets) / grad_accum_steps
    scaler.scale(loss).backward()
else:
    with torch.amp.autocast('cuda', dtype=torch.bfloat16):  # BF16 路径
        preds = model(images, pos_x, pos_y)
        loss = criterion(preds, targets) / grad_accum_steps
    loss.backward()  # 无需 scaler
```

- **收益**：代码简化 ~30%，消除 GradScaler 的 scale factor 管理，训练更稳定，显存略省（无 scaler 状态）
- **风险**：极低。BF16 比 FP16 更稳定。唯一需验证的是 UNI2-h backbone 中的 LayerNorm/Softmax 会自动保持 FP32（autocast 内置规则）
- **验证方式**：单患者 smoke test 1 epoch，对比 FP16 vs BF16 的 loss 曲线和 val PCC，应基本一致

#### 2.2 `torch.compile` （PyTorch 2.0+ JIT 编译）

```python
# main() 中，模型创建之后
model = torch.compile(model, mode="reduce-overhead")
# 或保守起步: model = torch.compile(model, mode="default")
```

- **收益**：训练速度 +10–30%（TorchBench 几何平均 1.8×，本项目 ViT 架构保守估计 15–25%）
- **风险**：
  - 首次运行编译耗时 30–120 秒（后续 epoch 无开销）
  - 动态 shape 会触发重编译（本项目 shape 固定，无此问题）
  - 可能与 `lora_utils.py` 中的手工 LoRA 注入有交互（需验证）
- **mode 选择**：
  - `"default"` — 平衡，先试这个
  - `"reduce-overhead"` — 小模型 + 小 batch 场景更优（本项目 batch_size=1-8 符合），会用 CUDA Graphs 额外加速
- **验证方式**：smoke test 1 epoch，确认无报错且 loss 正常下降

### 🟠 Tier 3 — 需要验证，中等收益

#### 3.1 `channels_last` (NHWC) 内存格式

```python
# 模型转为 channels_last
model = model.to(memory_format=torch.channels_last)

# 数据加载时转换（Dataset __getitem__ 或 DataLoader collate_fn 中）
image = image.to(memory_format=torch.channels_last)
```

- **收益**：CNN 层 15–30% 加速（ViT 的 patch embedding 卷积也会受益）
- **风险**：UNI2-h 是 ViT 架构，收益不如纯 CNN。需确保所有自定义层支持 NHWC。评估：**对本项目收益有限，可作为可选项**
- **建议**：Tier 1+2 实施后若仍想继续优化再尝试

#### 3.2 显存释放 → 增大 batch_size

BF16 + `zero_grad(set_to_none=True)` 可释放 30–40% 显存。将释放的显存用于增大 `batch_size`：

| 当前 | 优化后 | 效果 |
|------|--------|------|
| batch_size=4, FP16 | batch_size=6, BF16 | 吞吐 +50% |
| batch_size=1, FP16, accum=8 | batch_size=2, BF16, accum=4 | 吞吐 +100%，等价 batch 不变 |

**策略**：先实施 Tier 1+2，在 smoke test 中逐步上调 `--batch_size` 直到显存占用接近 14GB（留 2GB margin），找到最优值后固定。

### 🔴 Tier 4 — 有代价，按需启用

#### 4.1 Gradient Checkpointing

```python
# 已有 --grad_checkpointing 参数，但未见实际使用
from torch.utils.checkpoint import checkpoint

# 在模型前向传播中包装计算密集型层
outputs = checkpoint(model.block, inputs, use_reentrant=False)
```

- **收益**：显存 ↓30–50%（以计算换显存）
- **代价**：训练慢 15–25%（反向传播时重算中间激活）
- **适用场景**：当前显存已不够用，需要进一步增大 batch_size 时
- **当前评估**：16GB 显存在本项目的模型规模下大概率不需要。**暂不建议启用**，先通过 Tier 1–3 充分利用显存。

## 三、综合实施建议

### 推荐实施顺序

```
Step 1: Tier 1 全系列（TF32 + cudnn + fused AdamW + DataLoader）
        ↓ smoke test，确认 PCC 不变
Step 2: BF16 替代 FP16（核心改动）
        ↓ smoke test，对比 FP16 loss/PCC
Step 3: torch.compile
        ↓ smoke test，确认无 graph break
Step 4: 增大 batch_size（利用省下的显存）
        ↓ 找到最优 batch_size
Step 5: 正式训练
```

### 预期总收益

| 优化组合 | 预期加速 | 显存变化 | 安全性 |
|----------|:---:|:---:|:---:|
| Tier 1 only | 1.2–1.4× | 略降 | 🟢 绝对安全 |
| Tier 1 + BF16 | 1.4–1.7× | ↓20–30% | 🟢 极安全 |
| Tier 1 + BF16 + compile | 1.6–2.2× | ↓10–20% | 🟡 需验证 compile |
| 全套 + 增大 BS | 1.8–2.5× | 与当前持平 | 🟡 需验证 |

### 安全性保障措施

每次改动后的验证流程：
1. **Smoke test**：单患者 1 epoch，确认 loss 正常下降、无 NaN
2. **对标对比**：FP16 vs BF16 的 epoch 1 的 val_loss / val_pcc 差异应 <0.5%
3. **compile 验证**：设置 `TORCH_LOGS="graph_breaks"` 检查是否有意外 graph break
4. **全量训练**：通过 smoke test 后再启动正式训练

## 五、关键注意事项

### Windows 特殊考虑
- `num_workers > 0` 需要 `if __name__ == "__main__"` 保护 → 已有 `main()` 函数，满足
- `fused=True` AdamW 在 Windows + CUDA 11.8 下可用（PyTorch 2.0+）
- 服务器 PowerShell 启动命令保持不变，无需额外环境变量

### BF16 兼容性
- RTX 4080 (SM 8.9) 完全支持 BF16 → `torch.cuda.is_bf16_supported()` 返回 `True`
- 本机 RTX 4060 (SM 8.9) 同样支持 → 本地 smoke test 有效
- 唯一不支持的场景：CPU 训练 / 极旧 GPU (SM < 8.0)
- 已有 FP16 fallback 路径，兼容性无虞

### checkpoint 兼容性
- BF16 训练产生的 checkpoint 与 FP16 checkpoint **完全兼容**（模型权重始终 FP32 存储）
- 旧 FP16 checkpoint 可正常 resume，新训练自动切换到 BF16
- 唯一变化：checkpoint 中 `scaler_state_dict` 在 BF16 下为 `None`（load 时已有 try/except 保护）
