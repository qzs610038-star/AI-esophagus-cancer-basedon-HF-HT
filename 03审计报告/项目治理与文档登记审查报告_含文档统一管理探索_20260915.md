## 0. 结论摘要

- 总体裁定：**CONDITIONAL GO**。日常实验、交接与论文准备不受阻断——全部发现均为 `WARN` 级治理漂移，未发现科研泄漏、越权操作或虚构结论。唯一 **NO-GO** 项是“直接运行 `python deploy/pfmval_ops.py docs scan --write` 刷新文档 Registry”：dry-run 证明现有扫描规则会把 3 份手工登记的 active 文档降为 `historical`、把 48 份新文档（含 2026-09-14 的 Virchow2 消融方案）全部登记为 `historical`、并改写 5 个被 `current_state.json` 引用的自定义 `doc_id`。须先修规则再刷新。
- 五个最重要的发现：
  1. **文档 Registry 全量扫描停留在 revision 255（2026-09-04）**，其后只手工追加了少量条目。磁盘上至少 **110 份 Markdown 未登记**（47 份在扫描器覆盖目录内——dry-run 还会额外吸入 1 个 `.pytest_cache/README.md` 噪音文件，合计 48；63 份在扫描器从不覆盖的 `03审计报告/`、`maintenance_logs/`、`project_state/governance/`、`docs/`），另有根目录 2 份零散文档和 15 份实验包内文档未纳入任何登记。
  2. **Registry 的“分类”不能回答“这是什么、现在算不算数”**：286 份在册文档中仅 39 份（14%）有 `purpose`；240 份 `historical` 中绝大多数是扫描器“认不出就归 historical”的兜底结果，不是人工判断；`doc_role/related_docs/source_refs` 三个关系字段（2026-08-07 已批准设计）分别只填了 3/0/0 条。`availability` 字段有 198 份仍标 `local_only`，而它们自 DIR-20260905-002 起实际已被 Git 跟踪。
  3. **两份登记表互不引用**：`experiment_registry.json` 对文档目录仅 11 处旧引用（全部是 7 月前的 MPP1-5 计划），9 月的三个已接纳实验（`phase2_softlink_local_v2`、`phase2_softlink_contrastive_v3`、`phase2_spatial_warmstart_v1`）没有任何字段指向其部署方案 / 分析报告 / 学习指南；反向亦然。这是“不清楚哪个文件对应哪个”的直接根因。
  4. **多份入口/导航文档正文过时**：`README.md`（GitHub 门面）状态块停在 revision 258，正文仍描述 `.qoder/`（目录已不存在）、Linux 服务器迁移、`train_online_cls.py` 等旧脚本、“9 患者数据预计 7 月初到齐”；`PROJECT_GUIDE.md` 目录地图列出不存在的 `archive/`，却漏掉 `03审计报告/`、`maintenance_logs/`、`experiments/results/`；`01_指南与解读/01_README.md` 人工索引停更于 2026-07-12；`experiments/decision_log.md` 最后一条是 2026-07-11；`project_state/implementation_plans/README.md` 仍描述已退役的 W### 两阶段审批流程。
  5. **状态一致性小缺口**：`current_state.json.active_directive_ids` 漏列两条 `active` 指令（DIR-20260908-003、DIR-20260908-004，均已写入 AGENTS.md 正文）；`directives.jsonl` 中 DIR-20260912-001 被逐字重复记录两次；`active_plans` 仍把已 `failed/rejected` 关闭的 `mpp2_pathway_ridge_calibration` 与 LoRA/Gitee 时代的 `mpp_training` 列为 active。
- 修复建议分三档（详见第 4 节）：**一档**登记修正（修扫描规则→dry-run→刷新→重生成视图、补两条指令 ID、去重），低风险，用户一句话授权即可执行；**二档**生命周期裁决（约 12 项需用户逐项定 active/superseded/historical）；**三档**内容重写与结构改进（README 正文、目录索引替代方案、零散文件归位），需用户明确授权。
- 文档统一管理探索（第 5 节）的推荐结论：**不搬文件、不建第二套登记表**；在现有 Registry 上增加“主题（topic）+ 角色（doc_role）+ 关联实验（experiment_ids）”三个字段，用它们生成两张面向人的视图——“主题档案卡索引”回答“哪个对应哪个”，“方案评审台账”回答“审过什么、结论是什么、被谁取代”；新文档以 6 行 frontmatter 落地即登记，旧文档只对近 45 天约 60 份做一次性补录。

## 5. 探索：学习文档、部署方案与指南文件的统一管理

### 5.1 问题重述与根因

用户两点痛点：①不清楚哪个文件对应哪个；②以前审查过的方案容易遗忘，不好整体回顾。现场证据指向五个根因：

1. **按体裁分目录，不按主题**。同一主题（例如“软连接 v2.1”）的材料散在 `部署方案/`（方案 v1、v2、v2.1、决策与执行记录、编码提示词）、`分析报告/`（Fable 评审原文、建议筛选、排查清单、结果与机制分析、指标附表、图示说明）、`学习指南/`（两份）、`03审计报告/`、`02_组会汇报/`、`团队项目进度与结论/qzs/`、`experiments/phase2_softlink_local_v2/`（README、验收、交接说明）七处；仅 2026-09-06 至 09-14 就产生 ≥45 份文件。
2. **版本关系只存在于文件名**。v1→v2→v2.1→v3→v4→“最终建议版”→warmstart v1→Virchow2 的取代关系、哪版被执行、执行成了哪个实验，没有任何登记字段承载。
3. **Registry 的 lifecycle 不是人工判断**（historical 兜底），`purpose` 86% 为空，`doc_role/related_docs` 未填——机器登记表回答不了“这是什么、还算不算数”。
4. **两个 Registry 互不引用**（第 3 节 F）。
5. **面向人的索引全部失效**：01_README 停更、GIT_INDEX 名不副实、PROJECT_GUIDE 历史区 240 行平铺。

### 5.4 推荐方案：一组字段 + 两张视图 + 一条落地约定

**字段（写入 `document_registry.json`，schema 追加，全部可缺省）**

- `topic`：主题 ID（小写下划线，稳定不改名），一个文档只属一个主题；跨主题用 `related_docs`。
- `doc_role` 枚举扩充：`deployment_plan` / `analysis_report` / `learning_guide` / `audit_report` / `meeting_report` / `team_share` / `decision_record` / `handoff` / `review_material`（评审输入、提示词、底稿）/ `index_view`。
- `experiment_ids`：指向 `experiment_registry.json` 的 id 列表；experiment_registry 侧对称加 `document_refs`（只存 doc_id，不复制内容）。
- `status_note`：一句话人工状态（如“v2.1 已执行为 phase2_softlink_local_v2；v3/v4 为后续建议”），替代靠 lifecycle 猜。
- 继续使用现有 `lifecycle`（draft/pending_review/active/superseded/historical）、`supersedes/superseded_by`、`purpose`。

**视图 1：主题档案卡索引**（生成文件，建议落点 `学习报告/00_主题索引.md`，或若用户希望保留“学习报告”另作他用，则放 `01_指南与解读/00_主题索引.md`）

每张卡固定结构：主题名 → 一句话现状 → 关联实验（状态/evidence_status）→ 关联决策 DIR → 文档按角色分组并按日期排序（部署方案标版本链与“已执行/未执行/已取代”）→ 审计与评审结论 → 学习指南入口 → 待办（pending_review 清单）。

**视图 2：方案评审台账**（同一生成脚本产出，落点同上 `01_方案评审台账.md`）

| 方案 | 主题 | 日期 | 版本链位置 | 审计/评审 | 决策 DIR | 执行实验 | 结果分析 | 当前状态 |
|---|---|---|---|---|---|---|---|---|

按“未审→已审未决→已决未执行→已执行→已取代/已否决”排序，末尾附“pending_review 超过 14 天”“active 但 45 天未核验”两张提醒表。这张表就是用户要的“整体回顾”入口。

**落地约定（写入 `.agents/skills/pfmval-governance/SKILL.md` 一小节 + `experiments/_template/README.md` 文档区）**

1. 新写部署方案/分析报告/学习指南/审计报告时，文件前 6 行 frontmatter：`topic`、`doc_role`、`status`、`related`（doc 路径或 doc_id）、`experiment`（可空）、`supersedes`（可空）。
2. 文档落盘后同一轮对话内完成登记（`pending_review`），不等待周检。
3. 方案被审计 → 审计报告 `related` 指回方案；方案被决策 → 在 DIR 的 `affected_files` 中出现即自动挂到主题；方案被执行 → 实验登记 `document_refs` 指回方案。
4. 版本迭代用 `supersedes` 指向上一版，旧版 lifecycle 改 `superseded`（不删除、不改名）。
5. 周检（`maintenance_logs/weekly`）加两项自动输出：本周新增/变更 Markdown 与未登记清单（`git log --since` 可直接得出）；pending_review 超期清单。

**分阶段**

- 阶段 0（本报告）：只读盘点。
