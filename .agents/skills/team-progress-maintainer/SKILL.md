# 团队项目进度维护

## 必读与准备

1. 读取 `AGENTS.md` 和 `project_state/current_state.json` 相关字段；涉及实验结论时读取相关 Registry 记录。
2. 读取 `references/directory-and-routing-policy.md` 与 `references/approval-and-append-only-policy.md`。
3. 修改前运行项目严格检查：`python deploy/pfmval_ops.py agent start-check --strict`。
4. 对所有将被修改的既有维护文档建立临时快照。快照放在仓库外临时目录，不写入团队资料目录。

## 强制边界

- 只把用户已经显式审核并批准的内容写入正式维护目录。用户明确说明“已经审核”的材料可直接纳入。
- 未获批准时，只在对话中提交待审概要；不得提前创建正式结论、汇总索引或术语表条目。
- 禁止覆写、删除、替换、重排或移动任何既有维护内容。
- 新进展作为带日期的新段落追加。需要纠正既有表述时，保留原文，在需修正位置紧邻追加独立的“补充说明”块，不得修改原句。
- 补充说明必须写明日期、审核状态、原结论需要补充的原因、新证据和修正后的适用边界。
- 不把历史材料、探索性结果、计划或未导入结果写成稳定结论。
- 保留成员原始材料；不得为了统一格式而重排、重写或清理已纳入的成员文件。

## 执行流程

1. 确认材料归属成员及来源路径。
2. 提取准备写入的概要：方案、条件、结果、结论、下一步、完成日期、证据链接、图表需求。
3. 明确审核状态：`已批准`、`待审核` 或 `拒绝写入`。状态不明一律按 `待审核` 处理。
4. 获批后把材料追加到相应成员目录；必要时使用 `assets/member-progress-template.md`。
5. 按成果用途追加汇总索引：Phase2/3、论文写作、训练数据。使用 `assets/summary-index-template.md`，不在汇总中复制整份成员文档。
6. 首次出现的必要英文术语追加到 `团队项目进度与结论/英文专业术语速查表.md`，给出中文含义和当前项目中的具体解释。
7. 对内部流程简称进行展开。不得面向队友只写“门控”“合同”或 `NO-GO`；改写为“满足/未满足什么条件，因此下一步执行/停止什么工作”。
8. 使用 `scripts/validate_team_tree.py` 检查目录与链接。
9. 使用 `scripts/validate_append_only.py` 比较修改前快照与修改后目录；修正任务追加 `--correction-mode`。
10. 再次运行项目严格检查，报告新增内容、证据、验证结果和仍待审核事项。

## 写作要求

- 全部采用易懂、严谨、准确的中文；必要英文术语进入速查表。
- 每项结论突出：采用什么方案、比较什么条件、实际结果、结论、下一步及完成日期。
- 数值结论必须链接可核验结果文件；代码结论必须链接真实实现。
- 汇总索引必须指向成员原文，并标注所属板块和审核状态。
- 任何不确定项明确写“待补充”或“当前证据不足”，不得推断。

## 补充说明格式

在原内容紧邻位置追加，不改原文：

```html
<details>
<summary><strong>补充说明（YYYY-MM-DD，已获用户审核）</strong></summary>

- 原内容保留原因：……
- 需要补充或修正的事项：……
- 新证据：……
- 更新后的理解与适用边界：……

</details>
```
