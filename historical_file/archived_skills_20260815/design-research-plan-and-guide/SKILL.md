# 科研部署方案与学习指南设计

把“有哪些热门方法”转化为“本项目下一步最值得验证什么、如何排除替代解释、用户需要先决定什么”。部署方案规定实验合同，学习指南解释合同背后的推导；不得用学习指南替代可执行边界，也不得用论文结论冒充项目证据。

## 必读顺序

1. 完整读取项目 `AGENTS.md` 及其要求的当前事实源。
2. 读取用户指定的本地文件、云端方案、论文解读、原论文和代码；无法访问的来源明确标记为缺失。
3. 读取当前 active 部署方案、实验 Registry、已接纳结果和受保护资产边界；历史或 superseded 文档只作背景。
4. 需要独立完成声明或 GO/NO-GO 时，另用项目审计 Skill，不让本 Skill 自审自证。

PFMval 项目中读取 `references/科研边界.md`，并遵守项目既有审批、工作树、Gitee-only、防泄漏和证据等级约束。

## 核心原则

- 分开记录：项目事实、用户决定、文献事实、方案建议、推断、未知。
- 先锁定问题、指标和非目标，再讨论模型；不从论文架构反推项目目标。
- 首轮实验优先共享基线、互斥增量轴和容量匹配对照，使每个比较能回答一个问题。
- 论文只提供机制依据和候选实现；阈值、收益和适用性必须重新接受项目数据检验。
- 性能指标、机制诊断、治理硬门和用户决策门分层表达，不相互替代。
- 对创新性使用“候选组合”“待系统查新”等审慎表述；未完成查新不得宣称全球首创。
- 方案批准不等于代码、训练、服务器操作或结果接纳获批。

## 工作流程

### Evidence Intake and Boundary Lock（证据受理与边界锁定，EIBL-1）

提取用户目标、非目标、工程预算、评价痛点、下游动机和明确禁区。建立来源清单，使用 `references/证据矩阵.md` 标注来源类型、时效、证据等级和缺口。

### Evidence Comparison Matrix（证据对照矩阵，ECM-2）

逐份记录原始任务、输入输出、核心机制、实验设计、适用条件、可借鉴部分、任务错配和不能直接继承的结论。论文与代码实现不一致时分别陈述，并固定核验版本后才可提出复现结论。

### Route Causal Decomposition（路线因果拆解，RCD-3）

把候选路线拆成冻结基线、容量对照、单机制增量、关键机制对照和证据触发的后续复杂分支。优先设计最小实验矩阵，避免首轮同时改变结构、损失、数据和选择指标。

### Deployment Plan Construction（部署方案构建，DPC-4）

使用 `assets/部署方案模板.md`。至少写明事实边界、目标与非目标、来源取舍、实验合同、数据和防泄漏、指标与 checkpoint 选择、外部评估、风险、停止点、产物和用户决策。步骤首次出现时写中文与英文全称及对应缩写，避免无意义编号。

### Learning Guide Derivation（学习指南推导，LGD-5）

使用 `assets/学习指南模板.md`。对每个关键设计解释前置知识、参考设计原貌、本项目修改、修改原因、解决痛点、优势、风险和用户决策。困难概念用类比辅助，但紧随精确定义，不能用类比代替科学边界。

### Key Decision Digest（关键决策摘要，KDD-6）

当用户明确要求两份文档都详细，或生成后两份均超过 300 行时，强制执行：

1. 在部署方案标题和元信息之后、详细正文之前放置 2–4 个关键决策点。
2. 只选择会显著影响科学结论、因果归因、数据泄漏、外部效度、主要计算预算或后续路线的事项。
3. 每项包含决策问题、为何关键、可选方案与代价、建议默认值、用户需确认内容。
4. 使用稳定编号 `KDP-1` 至 `KDP-4`；学习指南顶部建立同编号章节，并在标题前显式写入 `<a id="kdp-1"></a>` 形式的 ASCII 锚点。
5. 部署方案每项链接到学习指南对应显式锚点，例如 `../学习指南/文件.md#kdp-1`。
6. 不用普通超参数、路径或命名问题占用关键决策名额。

若两份文档较短，仍在开头给出简短决策摘要，但可不建立完整深链区。

### Pair Consistency Validation（成对一致性校验，PCV-7）

按 `references/成对文档输出合同.md` 人工复核，再运行：

```powershell
python .agents/skills/design-research-plan-and-guide/scripts/validate_plan_guide_pair.py --plan <部署方案.md> --guide <学习指南.md>
```

有跨文档共享术语时可重复添加 `--required-term FBR --required-term CPGCR`。修复所有 ERROR；WARN 逐项解释或修复。不得为了通过校验删除真实风险、未知或反例。

### Human Approval Gate（用户审批门，HAG-8）

先在对话中呈现 2–4 个最关键决策供用户审批。获得明确批准后再按项目生命周期落盘、登记或创建实施方案。若用户只批准科学路线，不得推断其同时批准代码、训练、服务器或外部发布。

## 输出分工

- 部署方案回答：做什么、保持什么不变、如何比较、何时停止、什么证据允许进入下一阶段。
- 学习指南回答：为什么这样设计、参考方法原来怎样、本项目为何修改、用户应如何理解风险。
- 对话摘要回答：用户现在最需要先决定什么；不得用长文目录冒充决策摘要。

## 完成前检查

- 所有数值和项目状态均有事实源或明确标为拟议值。
- 共享基线、增量轴、选择指标和外部评估边界一致。
- 部署步骤与学习指南推导一一对应。
- 2–4 个 `KDP-*` 在两份长文中编号一致且深链有效。
- 文献原始设计、本项目改动和预期收益没有混写。
- 未把诊断性结果写成 accepted 结论，未把下游动机变成上游调参标签。
- 未越过用户批准范围。
