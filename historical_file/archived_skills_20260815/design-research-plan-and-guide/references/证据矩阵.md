# 证据矩阵

## 使用目的

在写方案前建立内部工作表，防止把不同强度、不同任务和不同时间点的材料混成同一种证据。只有帮助用户判断的内容才进入正式文档。

## 来源分级

| 来源类型 | 可支持的内容 | 不能自动支持的内容 |
|---|---|---|
| accepted 项目结果 | 当前项目在已登记合同下的实际表现 | 新机制必然有效、其他数据集可复现 |
| active 项目合同或用户指令 | 当前允许范围、指标、资产与审批边界 | 科学机制正确或性能提升 |
| 本地代码与配置 | 已实现行为、参数和接口 | 未实际运行的性能结论 |
| 原论文与补充材料 | 作者报告的任务、方法和结果 | 直接迁移到本项目的收益 |
| 官方代码 | 指定版本可观察到的实现 | 论文所有实验都使用该入口或配置 |
| 外部方案或论文解读 | 候选路线、比较维度和风险线索 | 原论文事实或项目已批准结论 |
| 专家或模型评估 | 批评、遗漏和备选设计 | accepted 项目事实 |
| 用户口述背景 | 研究动机、约束和待验证观察 | 未经登记的正式实验结果 |

## 建议字段

| 字段 | 填写内容 |
|---|---|
| `source_id` | 稳定简称 |
| `source_type` | 上表来源类型 |
| `question_answered` | 该来源实际回答什么问题 |
| `original_task` | 原始任务、数据、输入和输出 |
| `mechanism` | 核心机制，不写宣传性概括 |
| `reported_evidence` | 指标、消融和限制 |
| `project_fit` | 高、中、低，并写原因 |
| `adopt` | 本项目采用部分 |
| `modify` | 本项目修改部分及原因 |
| `defer_or_reject` | 暂缓或拒绝部分 |
| `uncertainty` | 未知、版本差异、待核验项 |

## 比较规则

1. 先比较任务和标签分布，再比较架构名称。
2. 分开评价科学适配性、工程适配性和证据成熟度。
3. 论文与代码存在差异时写成两个来源条目。
4. 项目没有直接证据时使用“提出假设”“用于探针”，不用“将提高”。
5. 负结果、无提升数据集和失效条件必须进入矩阵。
